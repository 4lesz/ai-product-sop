# 第 5 步：小步开发

一次只做一件事，做完一件验收一件。每次代码变化有一个编号 `KF-<日期>-<序号>`，做完 7 项必做才能说"改完了"。

## 先确认用哪套规则

1. 项目里有管开发的 skill 或规则（不论叫什么名字：`<项目>-dev`、`project-standards`、`.trae/rules/`、`AGENTS.md` 里的规则……，看内容是不是规定了改代码的流程）→ 按它做，本 skill 只补它没写到的
2. 项目有执行标准或等价文档（对照表见 `sop-start`）→ 按它做
3. 都没有 → 按本 skill 和 [../sop-standards/references/execution-standard.md](../sop-standards/references/execution-standard.md) 做，并建议用户先走第 4 步 `sop-standards`

**编号**：项目已经有自己的编号规则（例如 FR / AC / 阶段编号），沿用项目的；没有才用下文的 `KF-日期-序号`。交接文档、验收记录的文件名和位置同样以项目已有的为准。

## 开工前

1. 读 `docs/交接文档.md`（当前状态、未关闭问题、待决事项）、`docs/PRD.md` 对应功能、当前阶段的 `docs/specs/<阶段>/spec.md`、`README.md`
2. 找到这次要做的事对应的 **PRD 编号**和**验收条目**。没有 PRD 编号 → 先用 `sop-prd` 登记；没有验收条目 → 先补条目再写代码
3. 处理验收问题时，读对应验收记录，先在本地复现
4. `git status` 确认没有无关改动，不覆盖别人的工作；和别的会话并行时，先说好谁负责哪些文件
5. 要改数据结构而本地有真实数据时，先备份
6. 告诉用户本次编号和要做的事；需求不清楚、和 PRD 冲突、碰到"待决事项"就先问

## 写代码时

- 只做这次说好的事，不顺手加 PRD 里没有的功能
- 业务规则集中放、校验放后端、报错用中文
- 外部服务（AI 模型、微信、支付）走封装层，本地和测试默认用假的；专门测真接口时单独开会话、控制花费、只出报告
- 改了界面按 `docs/设计规范.md`，复用现有组件
- 碰到没想到的产品问题，停下来问；实在要先定一个默认做法，记进交接文档"待决事项"

## 7 项必做

1. **测试**：自动化测试全部通过；改了规则就补测试；不删测试、不放宽断言
2. **实际验证**：界面改动在浏览器手机尺寸 / 模拟器里把受影响的流程走一遍；后端改动调接口验证；看外观要截图，不能只看代码或只查数值。验证完恢复演示数据，删掉验证时上传的测试文件，停掉自己起的服务
3. **记下版本**：改动前后的提交号或代码指纹
4. **更新验收清单**：新功能加条目，行为变了改条目并标 `（KF-编号 修改）`；不用改也写原因
5. **检查验收原则**：要不要新环境、新账号、新工具？有没有新问题类型？不用改也写原因
6. **写交接条目**：按 [references/handoff-entry-template.md](references/handoff-entry-template.md) 加在交接文档"变更记录"最上面，同时更新"当前状态"
7. **其他文档**：README、部署说明、PRD 里受影响的地方

**小改动**（不改业务规则、数据结构、接口和用户流程，例如改文案、调样式、修小毛病）：测试和实际看一眼照做，交接只写一条"### KF-编号 · 小改动：……"，两项"改了什么""测试"；当天的小改动接着往这条里加。拿不准就按完整的 7 项。只改文档不用写交接条目。

做完后跑一次 `node scripts/sop-check.mjs`（项目里没有就跑插件的 `../../scripts/sop-check.mjs`），有问题先改掉。装了插件的 Claude Code 在每一轮结束时会自动检查并提醒；真正拦人的是 git 提交前的检查。

**中途要停下来问用户**（需求不清、碰到待决事项）时，先在交接文档加一条只写标题和"- 状态：进行中，还差：……"的条目，收尾检查就会放行；提交前必须把它写完整

## 什么时候停下来问

- PRD 和代码对范围或行为说法不一致
- 新行为没有验收条目
- 测试失败，而修复会改变产品行为
- 改数据结构没有迁移或备份方案
- 要加权限、加联网、加第三方 SDK、加收费服务
- 要提交、推送、部署（只在用户明确说了以后做）

## 不能做

- 在同一个会话里给自己的改动做验收（用 `sop-accept`，在另一个会话或子代理里做）
- 为了通过而放宽规则、删测试、改清单的预期结果
- 把没测过的写成"已通过"

## 最后回复用户

- 编号和一句话标题
- 改了什么，每项一行，列关键文件
- 测试结果、实际验证了哪些流程
- 版本：改动前 → 改动后
- 验收清单、验收原则分别改了什么
- 建议复验哪些条目（或要不要全量验收），建议新开会话验收
- 需要用户决定的事；需要用户在真机或外部平台看的，给出一步步的检查步骤
