# 第 6 步：独立验收

开发写完后，由**另一个会话**按清单逐条亲自点一遍。验收人只认清单和亲眼看到的结果。

## 先确认三件事

1. **是不是独立的**：当前会话刚改过代码，就提醒用户新开一个会话来验收，或者把验收交给 `sop-acceptance-reviewer` 子代理。记录里要写"验收方式"：新会话验收就写本会话 ID（打开项目时钩子会告诉你），它不能和被验交接条目"改动人"里的会话 ID 相同
2. **用哪套规则**：项目里有管验收的 skill 或规则（不论叫什么名字，看内容是不是规定了怎么验、怎么判定）→ 用它；有验收原则或等价文档（例如 `验收标准.md`，对照表见 `sop-start`）→ 按它；都没有 → 按 [../sop-standards/references/acceptance-principles.md](../sop-standards/references/acceptance-principles.md)。记录写在项目已有的位置和格式里（例如验收标准里的记录表）；项目没有才用 `docs/验收记录/`
3. **验什么**：全量验收还是复验；复验的范围（交接文档最近一条的"建议复验"）。没说清就问

## 步骤

1. **编号和版本**：本次编号 `YS-<今天日期>-<序号>`，记下当前提交号；确认验的就是开发交上来的那一版。告诉用户编号、版本、范围
2. **确认本机没有别的验收在跑**（端口被占、有别的会话或 AI 工具在操作），有就先问用户
3. **前置检查**：跑自动化测试（以及类型检查、lint、构建，项目有的都跑）。有失败 → 记"中止"，停下告诉用户
4. **准备环境**：恢复演示数据，用数据副本或临时库，不碰真实数据；启动预览，切到清单要求的尺寸 / 模拟器；有多个端的，把每个端都启动好，准备好清单执行说明里各角色的账号
5. **逐条执行**：按清单顺序做，每条留证据（页面文字、截图、接口返回、命令输出）。不能凭读代码判断。每条用清单写明的端和角色账号做；越权条目界面和接口都要试；跨端条目在上游端操作后，到下游端确认结果
6. **判定和定级**：每条记通过 / 不通过 / 无法验证；不通过和清单外问题按阻断 / 严重 / 一般 / 轻微定级，拿不准取高一级；清单外问题编号 `YS-…-Q1`
7. **写记录**：按 [references/record-template.md](references/record-template.md) 写 `docs/验收记录/<编号>.md`，在 `docs/验收记录/README.md` 索引表最上面加一行（索引格式在同一个模板的末尾；还没有索引就照它建）
8. **收尾**：停掉自己起的服务、删掉测试上传的文件、浏览器切回桌面尺寸

## 只能由人做的部分

界面先在第 3 步定下的替代环境里验（网页版、模拟器、自动化驱动工具）。替代环境也做不到的——真机、手机扫码、应用商店、支付、外部平台后台——验收人不操作，相关条目记"无法验证（需要产品负责人在 X 上看）"。在回复里把这些条目整理成一份给产品负责人的检查步骤：点哪里、应该看到什么、看完把结果和截图发回来。

## 复核别人的验收报告

其他 AI 工具或其他人交来"已通过"的报告时：

- 用命令输出和截图复核关键条目，特别是"测试 / 类型检查 / 构建通过"这类一跑就知道的
- 报告说"已在真机通过"却没有真机记录的，不采信
- 复核结果按本 skill 的格式另写一份记录，注明复核了哪份报告

## 规则

- 只写 `docs/验收记录/` 下的文件；不改代码、测试、清单、验收原则、交接文档、演示数据（临时文件可以放系统临时目录。用 `sop-acceptance-reviewer` 子代理验收时，它没有编辑工具，插件的钩子还会拦下常见的越界写入和 git 提交）
- 实际结果和清单不一致就判不通过，即使你认为清单写错了——在说明里写出你的判断
- 写完的记录不再修改

## 最后回复用户

- 编号、类型、版本、结论（通过 / 有条件通过 / 不通过 / 中止）
- 通过 / 不通过 / 无法验证各几条
- 不通过的条目和 Q 问题，每条一行，带严重程度
- 上一轮的问题哪些已确认关闭
- 需要产品负责人在真机或外部平台看的检查步骤
- 对清单和验收原则的修改意见（哪条不好做、哪里有空缺）
- 记录文件路径
