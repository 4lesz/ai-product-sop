# 第 1 步：确认需求

这一步只回答三个问题：**有哪几类人用（以及他们之间是什么关系）、各自要解决什么问题、做到什么程度算成功**。做法是产品负责人先用大白话说想法，AI 反过来追问，最后写成一页需求简报。不写代码，也不急着定技术。

## 做法

1. **让产品负责人用一两句话说想法和场景**。例："人想买东西但是纠结，去问网友"；"平板上的视频点投屏就能在投影仪上播，不要会员和广告"
2. **把用的人分成几类角色**（见下文"角色拆解"）。不能只停在"给谁用"：内容从哪来、谁来维护、谁审核、谁看数据，每个答案都可能是一类角色，后面要不要单独做一个端（例如运营后台）就从这里来
3. **一次性列出还缺的信息**，按下面分组问，不要挤牙膏。已经能从对话里推断的就写出推断让他确认，而不是再问一遍
4. **把目标定成可衡量的数字**。"帮助学习"不行，"2027 年广东专升本计算机类总分 420/500 以上"可以；"好用"不行，"点投屏到出画面 ≤ 3 秒"可以
5. **写清不做什么**，至少 3 条。日课从第一天就定了"只为这一场考试服务，不做通用学习 App"，后面很多取舍都有了依据
6. **提前查平台门槛**（见下文）。这是最容易做完才发现上不了线的地方
7. **内容型产品先建知识库**（见下文），再进入第 2 步
8. **写需求简报** `docs/需求简报.md`，按 [references/brief-template.md](references/brief-template.md)，发给产品负责人，**等产品负责人确认**后再进入下一步；回答里没覆盖的地方按默认处理的，在简报里标"默认"

## 追问清单

| 分组 | 要问清楚的 |
| --- | --- |
| 角色与场景 | 有哪几类人会用或参与（终端用户、运营 / 维护、审核、客服、看数据的人）？每类人在什么情况下用、多频繁、用什么设备？现在他们是怎么解决的、哪里不满意？他们之间谁给谁提供东西？（见"角色拆解"） |
| 目标 | 做成什么样算成功？用什么数字衡量？什么时候要用上？ |
| 范围 | 第一版必须有哪几件事？哪些明确不做？哪些以后再说？ |
| 平台 | 网页、小程序、安卓、iOS、电脑程序还是设备上的 App？在什么设备上用（手机 / 平板 / 电视遥控器 / 电脑）？ |
| 约束 | 预算（服务器、AI 接口要不要花钱、能花多少）、时间、主体资质（个人 / 个体工商户 / 公司）、合规要求（隐私、不联网、不碰版权） |
| 已有资料 | 有没有方案文档、截图、竞品、大纲、素材？先读这些 |
| 运行与维护 | 最后装在哪台机器、谁来维护？以后会不会交给别的 AI 工具（Trae 等）接手？会不会给朋友、同学用？ |
| 名字 | 产品叫什么（可以先用暂定名）？项目代号用什么（小写英文，例如 `gouhua`，不确定就由 AI 建议一个）？文档里怎么称呼产品负责人？ |
| 怎么做 | 要不要先搭项目骨架？要完整版流程还是轻量版（见 `sop-start`）？ |

## 角色拆解

产品负责人一开始通常只想到"最终用户"。但一个产品往往不止一类人在用：用户在前台用，背后有人上架内容、审核、处理投诉、改配置、看数据。这些人要做的事不一样，后面要做几个端（例如用户端和运营端）、每个端有哪些功能、谁能看到什么、验收时要用哪些账号，都从这一步来。漏掉一类角色，到开发后期才发现"内容没地方录入""举报没人能处理"，返工最大。

### 用五个问题找出所有角色

1. **谁在前台用？** 有没有不同身份（例如提问的人和回答的人、学生和家长、买家和卖家）？
2. **内容和数据从哪来？** 谁录入、上架、导入？（题库、商品、公告、配置）
3. **出了问题谁处理？** 谁审核内容、处理举报和投诉、封号、退款？
4. **谁要看结果？** 谁看数据、报表、日志？
5. **谁改规则？** 价格、额度、开关、文案由谁改，改了多久生效？

每个答案都对应一类角色；即使现在是产品负责人自己顺手做（例如直接改数据库、改代码里的常量），也要列出来，写明"第一版由产品负责人手动做"。这是隐藏的运营需求，第 3 步要决定是做一个运营端，还是先用脚本、表格顶着。

### 每类角色写清楚

| 要写的 | 说明 |
| --- | --- |
| 角色 | 例如"提问者""回答者""运营" |
| 是谁 | 什么样的人、大概多少人；是不是产品负责人自己 |
| 要做什么 | 他用这个产品完成哪几件事 |
| 怎么用 | 用什么设备、多频繁、懂不懂技术 |
| 上下游 | 从谁那里拿什么、给谁提供什么。例如"运营上架题库 → 学生练习 → 运营看错题统计" |

例子（问问，购物决策社区）：提问者（纠结买什么的人，发帖问）、回答者（网友，回帖给建议）、运营（审核内容、处理举报）。前两类在同一个小程序里用，运营在单独的后台里用，运营是另外两类的上游：审核不过的帖子用户看不到。

### 先初步判断要几个端

角色列完后，写一句初步判断：哪些角色可以共用一个端（例如提问者和回答者都在用户端里，只是身份不同），哪些角色看起来需要单独的端（例如运营后台）。这只是初判，**最终分几个端在第 3 步作为决定点由产品负责人拍板**。

只有一类人用的产品（例如只给自己用的工具），也要过一遍五个问题，确认确实没有维护和运营的需要，然后在简报里写明"只有一个角色"。

## 提前查平台门槛

在写 PRD 之前就要确认，否则可能白做：

- **微信小程序**：主体类型能选哪些类目（个人主体不能选"社区 / 论坛"，发帖评论类产品上不了线）；是否需要小程序备案、ICP 备案、特殊资质；隐私保护指引要声明哪些接口
- **应用商店 / 安装包分发**：签名、权限、是否允许侧载；目标设备能不能装第三方 App
- **AI 接口**：用哪家、按量还是套餐、套餐条款是否允许拿来给自己的应用当后端（不允许就不要用，也不要想办法绕过）
- **内容与版权**：有没有用户发内容（要内容审核）、会不会碰到会员 / DRM / 版权内容（不破解、不绕过）

能联网就查官方文档，把链接写进需求简报的"平台门槛核对"；不能联网就按已知情况写，标"未核实"。查不到确切规则的，写进"待确认"，并告诉产品负责人去哪里查。

## 内容型产品：先建知识库

学习、考试、题库、知识问答这类产品，代码要围绕内容设计。先把内容整理清楚：

- 在 `knowledge/` 下按主题写 Markdown：概览、考试或业务规则、科目 / 章节结构、评分方式、用户画像、资料来源
- 每条信息标来源等级：【官方】【机构整理】【经验判断】；拿不准的放进"待核实清单"
- 给代码用的结构化数据单独放一份（例如 `outline.json`），ID 一旦定了永不改，过时内容标 `deprecated`
- 用户画像的每个字段写明来源和谁能改（只能用户改 / AI 只能建议 / 自动计算）

## 完成标准

- 产品负责人能用三句话讲清楚这个产品
- 角色列全：五个问题都问过，每类角色写了要做什么和上下游；有初步的分端判断（只有一类人用也写明）
- 目标有数字
- "不做什么"至少 3 条
- 平台门槛查过，查不到的写进待确认
- `docs/需求简报.md` 已确认（内容型产品还有 `knowledge/`）

做完进入第 2 步 `sop-prd`。
