# 第 2 步：写 PRD

PRD 是产品规则的最终依据：代码、验收、争议都以它为准。AI 按下面的结构起草，产品负责人逐节看、改、确认。

## 前提

`docs/需求简报.md` 已确认（或对话里已经问清了用户、目标、范围、不做什么）。没有就先用 `sop-discover`。

## 做法

1. 按 [references/prd-template.md](references/prd-template.md) 写 `docs/PRD.md`
2. 功能逐条编号 `F01`、`F02`……，每条标优先级：P0（第一版没有就不能用）、P1（应该有）、P2（有更好），并标属于哪个端（见下文"角色与端"）
3. 里程碑每个写一句**能实际验证的关卡**，例如"平板上的 B 站能搜到投影仪并播放 1080p"
4. 非功能需求写成数字，写不出数字的先写意图，第 4 步定标准时再补"（补充）"阈值
5. 待确认问题单独列在最后，不要埋在正文里
6. 给产品负责人一份大白话摘要：分几个端、各给谁用，P0 有哪些、明确不做哪些、几个里程碑、还有哪些待确认问题需要他回答
7. **等他回复确认**，没确认不进入下一步；确认后在变更记录写 1.0 版

## 写法要求

- **每条功能都有编号**。后面的方案、代码、验收清单、交接条目都引用这个编号，才对得上号
- **"不包含"和"非目标"和功能一样重要**。例如一个投屏 App 写了"不联网上报"，后来想做应用内公告时，AI 就据此指出"从服务器拉公告"违反承诺，改成把公告写进安装包
- **规则写具体**：字数上限、次数上限、时间（"满 7 天提醒"）、谁能看见、什么时候能改
- **技术方案只写概要**：选型和理由，细节留给第 3 步的阶段方案

## 角色与端

需求简报里列了几类角色，PRD 就要把它们落到"端"上（端也常叫"版本"，例如用户端、运营端）。第 3 步还没拍板分几个端时，先按简报的初步判断写，标"（待第 3 步确认）"。

- **端的清单**：每个端给哪些角色用、在什么平台（小程序 / 网页后台 / App）、怎么登录、谁能开通账号
- **功能标端**：功能表的"端"一列写"用户端""运营端"或"共用"。共用的功能写清各端的差别，例如"帖子详情：用户端只能看和回复，运营端还能下架"
- **只写一份共用功能**：两个端都有的功能（登录、详情页、搜索）编一个号，不要每个端各编一个，否则改规则时容易只改了一边
- **权限表**：功能 × 角色，每格写"能 / 不能 / 只能看 / 只能改自己的"。越权（普通用户能做运营的事）是最严重的一类问题，第 4 步会照这张表写越权验收条目
- **上下游流程**：上游端的操作怎么影响下游端，要写清楚多久生效、下游看到什么。例如"运营下架帖子 → 用户端立刻看不到，发帖人收到通知"
- **里程碑顺序**：下游端依赖上游端的内容时（用户端要有题目才能练），第一个里程碑就要让上游至少能用最简单的方式录入，哪怕先是一个导入脚本，不能等用户端做完才发现没有内容

只有一个角色的产品，写一句"只有一个端"，跳过功能表的"端"一列和权限表。

## 中途改需求

做到一半想加或改功能时：

1. 先登记进 PRD：新功能在功能表里接着编号，标"（YYYY-MM-DD 新增）"；改过的数值写"（YYYY-MM-DD 修订：原为 40MB）"
2. 同步验收标准 / 验收清单（第 4 步之后才有）
3. 在 PRD 变更记录加一行，版本号 +0.1
4. 然后才进入第 3 步（大改动）或第 5 步（小改动）

口头说的需求不能作为验收依据。用户问"能不能……"时，先说清这需要登记成新需求、会影响哪些地方，再问他要不要加。

## 文档分工（功能多了以后）

| 文档 | 回答 |
| --- | --- |
| `PRD.md` | 做什么、为什么、优先级、成功标准 |
| `specs/<阶段>/spec.md`（大项目可再加一份 `设计方案.md` 写整体架构；它和画界面风格的 `设计规范.md` 是两回事） | 怎么做、决策记录 |
| `验收清单.md` | 怎么证明做对了 |
| `README.md` | 怎么上手、现在进度 |

文档冲突时按这个顺序同步：PRD → 设计方案 → 验收清单 → README → 项目规则。

## 完成标准

- 每条功能有编号和优先级；有多个端的，每条功能标了端，有权限表和上下游流程
- 有"不包含 / 非目标"
- 每个里程碑有一句可验证的关卡
- 待确认问题单独列出
- 产品负责人确认，变更记录有 1.0

做完进入第 3 步 `sop-spec`。
