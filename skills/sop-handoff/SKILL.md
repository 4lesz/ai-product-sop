# 第 8 步：交接与反馈

AI 会话不会记得上一个会话做过什么，项目的"记忆"只能靠文档。交接文档就是项目的大脑：任何新会话、接手的人或工具，读完它就能接着干。

## 交接文档的结构

按 [references/handoff-doc-template.md](references/handoff-doc-template.md) 维护 `docs/交接文档.md`：

| 部分 | 写什么 | 什么时候改 |
| --- | --- | --- |
| 当前状态 | 当前版本、最近一轮验收、测试数量、运行方式、线上版本；只留最新 | 每次代码变化、验收、部署后 |
| 未关闭问题 | 验收发现还没修的问题；关闭时写明哪次变化关的 | 验收后、修复后 |
| 待决事项 | 需要产品负责人拍板的事；开发先定的默认做法 | 有新问题时、拍板后移到"已定" |
| 已定 | 拍过板的决定，带日期和原话 | 拍板后 |
| 环境 | 线上环境、数据库、存储、服务版本（不写密码） | 部署后 |
| 变更记录 | 每次代码变化一条，最新在最上面 | 每次代码变化 |

## 别让它变得太长

- 小改动只写一条短条目，当天的合并在一起（见执行标准）
- "当前状态"只留最新的；已关闭的问题、已执行完的计划移走
- 变更记录超过 20 条，把较早的原样挪到 `docs/交接归档/变更记录-YYYY-MM.md`，交接文档里写一句归档在哪（检查脚本会提醒）

## 什么时候更新

- 每次代码变化（第 5 步的第 6 项）
- 每轮验收之后：把结论、未关闭问题、清单意见登记进来
- 每次部署之后：线上版本、提交号、冒烟结果
- 产品负责人在真机 / 外部平台看完反馈之后
- 会话快结束、额度快用完、上下文快满时：先把进度写进去再停

## 新会话接手

1. 读 `CLAUDE.md` / `AGENTS.md`、交接文档"当前状态""未关闭问题""待决事项"
2. 用 `sop-start` 判断现在在哪一步
3. 告诉用户：项目现在的状态、上次停在哪、你准备做什么

交接文档可能过期：接手时用 git log、最近的验收记录和最近的报告核对"当前状态"，对不上就先补交接文档再干活。会话中途断了（额度用完、上下文满了）也一样，不要凭印象继续；核对不清的地方问用户。

## 换工具或多个 AI 协作

- **规则写进各工具都读的文件**：`CLAUDE.md`（Claude Code）、`AGENTS.md`（通用）、`.trae/rules/`（Trae）、`.agents/`（WorkBuddy 等）。硬性规则每条一句，持续追加
- **分工写清楚**：一种可行的分工是"一个负责开发、一个负责验收、一个负责修复"，用文件交接（见 [references/multi-agent-protocol.md](references/multi-agent-protocol.md)）
- **并行时划好文件边界**：两个会话或工具不能同时改同一批文件；开工前说好谁负责哪些
- **同一台电脑同一时间只做一轮验收**
- **别人交来的结论要复核**：别的工具说"已通过"，用命令输出和截图核一遍
- **别的工具写的文件不乱动**：不是本次任务产生的文件，没经用户同意不提交、不修改

## 反馈变成新需求

产品负责人自己用了、朋友试了、真机看了以后提的意见，以及 AI 做的评估报告、代码审查报告、真实接口测试报告里列出的问题，都按下面处理：

1. 原话记下来
2. 分类：缺陷（和 PRD / 清单不一致）→ 登记为未关闭问题，走第 5 步；新需求或改需求 → 走 `sop-prd` 登记；体验问题 → 列给产品负责人决定要不要做
3. 新需求多了，按价值和成本排个序给产品负责人选，决定下一阶段做什么，回到第 3 步

## 完成标准

- 交接文档"当前状态"是最新的
- 新会话只读交接文档和 `CLAUDE.md` 就能说清项目在哪、下一步做什么
- 待决事项都列给了产品负责人
