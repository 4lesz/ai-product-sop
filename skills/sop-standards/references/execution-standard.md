# <项目名>执行标准

> 这是通用模板。复制到项目的 `docs/执行标准.md` 后，把 `<尖括号>` 换成项目自己的内容，删掉不适用的行。项目没有自己的执行标准时，AI 直接按本文执行。

本标准适用于所有修改代码的人和 AI 会话。核心规则只有一条：**代码每变一次，都要同时更新交接文档、验收清单和验收原则，三样都处理完才算这次改动完成。**

## 1. 文档体系

| 文档 | 位置 | 作用 | 谁来改 |
| --- | --- | --- | --- |
| PRD | `docs/PRD.md` | 做什么、为什么、优先级；产品规则的最终依据 | 产品负责人确认后才改 |
| 阶段方案 | `docs/specs/<阶段>/spec.md` | 这个阶段怎么做、决定点和结论 | 开发写，产品负责人拍板 |
| 设计规范 | `docs/设计规范.md` | Logo、配色、字体、组件 | 产品负责人确认后才改 |
| 执行标准 | `docs/执行标准.md`（本文） | 怎么改代码、改完要做什么 | 产品负责人确认后才改 |
| 验收原则 | `docs/验收原则.md` | 怎么判定通过、问题怎么定级 | 每次改代码的人检查；改判定标准要产品负责人确认 |
| 验收清单 | `docs/验收清单.md` | 逐条可操作的验收项，每条有编号 | 每次改代码的人 |
| 验收记录 | `docs/验收记录/` | 每轮验收一份 | 只有验收人写 |
| 交接文档 | `docs/交接文档.md` | 当前状态、未关闭问题、待决事项、已定、变更记录 | 每次改代码的人 |
| 部署说明 | `docs/部署说明.md` | 一步步上线、上线后的冒烟测试 | 改了部署方式的人 |
| 开发 skill | `.claude/skills/<项目>-dev/` | 开发会话的规则，改代码时加载 | 跟着本标准同步 |
| 验收 skill | `.claude/skills/<项目>-acceptance/` | 验收会话的规则，做验收时加载 | 跟着本标准和验收原则同步 |

"代码"指：`<源码目录、测试目录、脚本、依赖清单、构建和部署文件>`；依赖目录和构建产物不算。只改文档不算代码变化，不需要走第 3 节。

## 2. 编号

| 对象 | 格式 | 例子 | 说明 |
| --- | --- | --- | --- |
| 功能需求 | `F<两位数>` | `F18` | 在 PRD 里编，永不复用 |
| 代码变化 | `KF-<日期>-<序号>` | `KF-20261103-01` | 一次代码变化一个编号，序号是当天第几次 |
| 验收轮次 | `YS-<日期>-<序号>` | `YS-20261103-01` | 每轮验收一个，复验也要编号 |
| 清单外问题 | `<验收编号>-Q<n>` | `YS-20261103-01-Q1` | 由验收人编号 |
| 清单条目 | `<节>.<条>` | `19.2` | 永不改号、永不复用 |
| 代码版本 | git 提交号 | `3ac695f` | 没用 git 时用代码指纹 |

编号用掉就不再复用。引用时写全，例如"KF-20261030-01 修复了 YS-20261029-03-Q1"。

## 3. 每次代码变化必做

按顺序做完下面 7 项，才能说"改完了"。任何一项做不到，就在交接文档里写明原因，并告诉产品负责人。

1. **测试**：自动化测试全部通过（`<测试命令>`）。改了业务规则必须补测试；不能删测试或放宽断言来让测试通过
2. **实际验证**：改了界面，就在 `<浏览器手机尺寸 / 模拟器>` 下把受影响的流程走一遍；只改了后端，就调接口验证。改了多个端共用的部分（数据、规则、接口、组件），受影响的每个端都要走一遍；改了权限，要用低权限账号试一次越权。验证完把演示数据恢复原样（`<恢复命令>`）
3. **记下版本**：记下改动前后的提交号或代码指纹
4. **更新验收清单**：按第 4 节改；没有要改的，也要写"验收清单：无变化"和原因
5. **检查验收原则**：按第 5 节判断；不需要改，也要写"验收原则：无变化"和原因
6. **写交接条目**：按第 6 节的格式，在交接文档"变更记录"最上面加一条，同时更新"当前状态"
7. **其他文档**：运行方式或目录变了改 `README`；部署方式变了改部署说明；产品规则变了同步 PRD

"说明原因"不能只写"无"，要写清为什么不受影响，例如"只改了样式，没有改变任何条目的预期结果"。

**小改动可以简化**：不改业务规则、数据结构、接口和用户能看到的流程的改动（改文案、调样式、修一个不影响规则的小毛病），第 1、2 项照做（测试、实际看一眼），第 3–5、7 项可以省略，第 6 项写成一条简短的"小改动"条目（格式见第 6 节）。当天的小改动接着往同一条里加，不用每次新开一条。拿不准算不算小改动，就按完整的 7 项做。**只改文档**（包括本标准、PRD、清单的措辞）不算代码变化，不用写交接条目。

## 4. 验收清单的更新规则

| 代码变化 | 清单怎么改 |
| --- | --- |
| 新增功能或规则 | 在对应小节末尾追加条目，编号接着往下排；没有合适的小节就新开一节 |
| 已有功能的行为变了 | 改对应条目的"操作"或"预期结果"，末尾标 `（KF-编号 修改）` |
| 删除功能 | 保留编号，内容改成 `（已废弃，KF-编号）`，不要删掉这一行 |
| 修复缺陷 | 清单里没有能覆盖这个缺陷的条目，就补一条，防止复发 |
| 验收时发现清单写错了 | 修正条目，标 `（YS-编号 反馈修正）` |

每条都写成"操作 → 预期结果"，预期结果具体到能看到的文字或数字。条目之间有依赖（后面的数字取决于前面的操作），要在条目里写明。

## 5. 验收原则的更新规则

改完代码后对照这几个问题：

- 验收需要新的环境、账号、工具或数据准备吗？
- 出现了现有严重程度定义覆盖不到的问题类型吗？
- 改动影响复验范围的划定吗（例如模块之间多了依赖）？
- 最近的验收记录有没有指出原则本身的空缺或矛盾？

有任何一个"是"，就改 `验收原则.md`，在文末修订记录加一行。涉及判定标准（结论档位、严重程度、通过条件）的改动，先问产品负责人。

## 6. 交接条目格式

```markdown
### KF-YYYYMMDD-NN · 一句话标题

- 日期：YYYY-MM-DD
- 改动人：人名 / AI（模型名）
- 起因：产品负责人的原话，或对应的验收编号
- 改了什么：每项一行，写关键文件
- 测试：N 项通过；新增 / 修改了哪些测试
- 实际验证：在浏览器、接口或模拟器上走了哪些流程
- 版本：改动前 → 改动后
- 验收清单：新增 / 修改 / 废弃了哪些编号，或"无变化（原因）"
- 验收原则：改了哪一条，或"无变化（原因）"
- 其他文档：改了哪些
- 建议复验：条目编号，要不要全量验收
- 遗留问题：没做完的、需要产品负责人决定的
```

小改动的条目：

```markdown
### KF-YYYYMMDD-NN · 小改动：一句话
- 改了什么：<文件>：<改了什么>
- 测试：N 项通过
- 改了什么：<当天的下一个小改动>；测试：N 项通过
```

"当前状态"只保留最新情况：当前版本、最近一轮验收、未关闭问题、待决事项。问题关闭时从未关闭列表移走，写上是哪个 KF 关闭的。

变更记录超过 20 条时，把较早的条目原样挪到 `docs/交接归档/变更记录-YYYY-MM.md`，交接文档里只留最近的，并在变更记录开头写一句"更早的记录见 docs/交接归档/"。挪动时不改条目内容。

## 7. 开发与验收的配合

1. 开发按第 3 节完成改动，交接条目写清"建议复验"
2. 验收人在另一个会话里按验收原则做复验或全量验收，写验收记录
3. 不通过的条目和 Q 问题回到交接文档"未关闭问题"，由下一次 KF 处理
4. 写代码的会话不给自己验收

## 8. 技术约定

> 按项目填写。下面是三个项目都用过的通用约定。

- 业务规则（数值、上限、权重）集中放在一个地方（例如 `RULES` 常量），前端从接口读取，不在多处写死
- 校验放在后端；报错信息用中文、说人话
- 有多个端时：数据、业务规则、接口各端共用一套，不为每个端各写一份；每个接口在后端校验角色权限，不能只靠界面隐藏按钮
- 外部服务（AI 模型、微信、支付、短信）统一走一个封装层；本地和测试默认用假的（mock），专门测试时才连真的
- 有一份演示数据和一条恢复命令，开发和验收都从同一个已知状态开始
- 改数据结构：同时写迁移；本地有真实数据时先备份
- 加依赖要说明理由和替代方案；加权限、加联网、加第三方 SDK 先改 PRD
- 界面按 `docs/设计规范.md` 做，新页面复用现有组件
- 代码用 git 管理，远程用私有仓库；只在产品负责人说"提交""推送"时才做

## 9. 需求变更

- 需求变更先改 PRD，再改本标准和代码；口头说的不作为验收依据，要先登记
- 新加的需求在 PRD 里标日期；改过的数值写明原来是多少
- 为了能实际测量而补的阈值标"（补充）"，列给产品负责人确认

## 10. 经产品负责人同意的例外

| 日期 | 例外 | 条件 |
| --- | --- | --- |
| | | |

偏离本标准的做法（例如真机验收还没做就先开始下一阶段）必须在这里登记，写明补做的条件。

## 11. 禁止事项

- 为了让测试或验收通过，放宽业务规则、删测试、改清单的预期结果
- 修改已有的验收记录
- 改动、复用编号，或删除已废弃的清单条目
- 做 PRD 里没有、也没经产品负责人同意的功能或规则
- 只在界面上隐藏按钮、不在后端校验权限
- 跳过交接文档、验收清单、验收原则中的任何一项就宣布完成
- 把没有证据的事写成"已通过"（例如没在真机上测却写"真机通过"）
