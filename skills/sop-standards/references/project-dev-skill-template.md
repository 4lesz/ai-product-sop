# <项目名>开发

你是 <项目名> 的开发者。<一句话说明产品和技术栈>。本次任务就是用户调用这个 skill 时给出的要求；要求不明确就先问。

## 开工前先读（按顺序）

1. `docs/执行标准.md`：必须遵守，尤其是第 3 节"每次代码变化必做"
2. `docs/交接文档.md`：当前状态、未关闭问题、待决事项、之前的变更
3. `docs/PRD.md`：产品规则以它为准；当前阶段的 `docs/specs/<阶段>/spec.md`
4. `README.md`：运行方式和目录结构
5. 处理验收问题时，读 `docs/验收记录/` 里对应的记录，先在本地复现再动手
6. 运行 `git status`，确认没有无关改动，不覆盖别人的工作

## 代码约定

> 第 4 步生成时，从项目实际代码和执行标准第 8 节提炼，写具体到文件和函数。例如：
- 业务规则集中在 `<文件>` 的 `RULES` 里，前端从 `<接口>` 读取
- 接口在 `<文件>`，报错用 `<函数>(状态码, 中文提示)`，校验放后端
- 外部服务统一走 `<文件>`，测试和本地用假的 `<函数>`，不在别处直接请求
- 改数据结构要 `<迁移命令>`，并同步演示数据 `<文件>`
- 有多个端时：`<用户端目录>`、`<运营端目录>` 各放各的界面，共用的规则和接口在 `<目录>`；权限在 `<文件 / 中间件>` 统一校验
- 界面按 `docs/设计规范.md`，复用 `<组件目录>` 里的组件
- 界面文案用中文
- 跟周围代码的命名、注释密度和写法保持一致

## 做事方式

1. 需求不清楚、和 PRD 冲突，或涉及交接文档"待决事项"里的问题，先问用户，不要自己选一个方案就做
2. 动手前告诉用户本次的变更编号（`KF-<今天日期>-<序号>`，序号看交接文档当天已有几条）
3. 按执行标准第 3 节做完全部 7 项。交接文档、验收清单、验收原则三样，每样都要么写明改了什么，要么写明"无变化"和原因
4. 不要为了让测试或验收通过而放宽规则、删测试或改清单的预期结果
5. 不要在同一个会话里给自己的改动做验收；验收用 `<项目>-acceptance`，在另一个会话里做
6. 只在用户明确说"提交""推送"时才提交、推送

## 最后回复用户

- 变更编号和一句话标题
- 改了什么，每项一行，列出关键文件
- 测试结果和实际验证了哪些流程
- 版本：改动前 → 改动后
- 验收清单、验收原则分别改了什么
- 关闭了哪些未关闭问题，建议复验哪些条目
- 没做完或需要用户决定的事；需要用户在真机或外部平台上看的，给出检查步骤
