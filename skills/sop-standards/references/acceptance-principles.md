# <项目名>验收原则

> 通用模板。复制到项目的 `docs/验收原则.md` 后按项目修改。项目没有自己的验收原则时，验收人直接按本文执行。

验收的目的，是确认代码的实际表现符合验收清单和 PRD。验收人只记录看到的事实，不修复问题。

## 1. 基本原则

1. **亲自操作，用事实作证**：每条都要实际操作并观察结果，证据是页面文字、截图、接口返回或命令输出。不能凭读代码推断"应该会通过"；口头说明不算证据
2. **以清单为准**：实际结果和清单的预期不一致就判"不通过"，即使验收人认为是清单写错了。验收人可以在说明里写出自己的判断，由开发在下一次改动中修正清单
3. **验收独立**：写代码的会话不给自己验收；验收人只写 `docs/验收记录/`，不改其他任何文件
4. **从已知状态开始**：每轮开始前恢复演示数据（`<恢复命令>`）；按清单顺序执行，后面的条目可能依赖前面的操作
5. **前置检查不过就停**：自动化测试有失败，本轮记"中止"，不再往下验
6. **记录不可改**：写完的验收记录不再修改；发现有误，在下一轮记录里说明
7. **只用本机和副本**：不连线上服务器和真实数据库，不动真实数据（用副本或临时库），不操作外部平台后台。条目需要的工具本机没有时，记"无法验证"并写明缺什么
8. **能让 AI 操作的环境优先，剩下的由产品负责人看**：界面在第 3 步定下的替代环境里验——同一份代码编出的网页版、模拟器、自动化驱动工具（例如小程序的 miniprogram-automator），以替代环境的表现判定。替代环境也做不到的（真机、扫码、应用商店、支付、外部平台后台）不在验收范围，记"无法验证"，由产品负责人按开发给的检查步骤看，结果记入交接文档
9. **同一台电脑同一时间只做一轮验收**：几轮同时跑会抢端口、互相清掉数据，结果谁的都不可信。开始前看有没有别的验收在跑，有就先问用户
10. **每个角色都要验**：有多个端或多类角色的，用各角色的演示账号分别操作；越权（低权限账号能做高权限的事，或能看到、改动别人的数据）一律按"阻断"定级；改了共用部分（数据、规则、接口、组件）的，受影响的每个端都要验
11. **复核别人的结论**：其他人或其他 AI 工具交来的"已通过"，要用命令输出和截图复核，不直接采信

## 2. 单条结果

| 结果 | 什么时候用 |
| --- | --- |
| 通过 | 实际结果和预期一致 |
| 不通过 | 实际结果和预期不一致，或操作中出错；写清实际看到了什么，按第 3 节定级 |
| 无法验证 | 当前环境做不了（需要真机、需要外部账号），写明原因；不能因为麻烦就标这个 |

一条里有部分步骤失败，就记"不通过"，不拆成"基本通过"。

## 3. 问题严重程度

| 级别 | 定义 | 例子 |
| --- | --- | --- |
| 阻断 | 核心流程走不下去，或数据丢失、越权、安全和隐私问题 | 无法发帖；普通用户能进运营后台；偷偷联网上报 |
| 严重 | 核心规则算错，或结果和 PRD 矛盾，或硬指标不达标 | 积分算错；体积超上限；必填项不填也能提交 |
| 一般 | 能用，但会误导用户、产生矛盾数据，或有明显体验缺陷 | 并列时只标一个；返回后列表丢失 |
| 轻微 | 文案、样式、提示语问题，或清单写法与正确的产品行为不一致 | 措辞不准；红字不随输入消失 |

拿不准时取更高的一级，并写出理由。

## 4. 本轮结论

| 结论 | 条件 |
| --- | --- |
| 通过 | 全部条目通过，没有清单外问题，或清单外问题都是轻微 |
| 有条件通过 | 没有阻断和严重问题；有一般或轻微的不通过条目或清单外问题，或有"无法验证"的条目 |
| 不通过 | 有任何阻断或严重问题 |
| 中止 | 前置检查失败；环境问题无法继续；或用户要求停下 |

"中止"的记录照常写完：做了的照实记，没做的写"本轮未验"，说明里写清原因。中止的那一轮不算验收过，重新验时另起一轮、用新编号。

## 5. 复验与全量验收

| 类型 | 什么时候做 | 范围 |
| --- | --- | --- |
| 复验 | 修复了问题，或做了局部改动 | 交接条目"建议复验"列出的条目、这些条目所在小节的其余条目、要关闭的 Q 问题的复现步骤 |
| 全量验收 | 对外发布或内测前；改了核心业务规则；改了数据结构；改了权限；距上次全量验收已有 3 次及以上代码变化 | 全部条目 |

修复后必须重跑整个条目，不只跑失败的那一步。
