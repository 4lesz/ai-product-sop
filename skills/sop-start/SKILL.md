# 产品开发 SOP · 总入口

这套 SOP 适用于"一个人当产品负责人、AI 当开发团队"的做法。产品负责人只做判断和拍板，AI 负责追问、写文档、写代码、验收；写代码的会话和验收的会话必须分开。

## 角色

| 角色 | 由谁担任 | 负责 | 不做 |
| --- | --- | --- | --- |
| 产品负责人 | 用户本人 | 提需求、回答追问、在决定点上拍板、看真机和外部平台、填密钥和登录、说"提交 / 推送 / 发布" | 不写代码 |
| 开发会话 | AI 会话 | 追问需求、写 PRD 和方案、列决定点、写代码和测试、自测、写交接条目 | 不给自己验收；不加产品方案里没有的功能 |
| 验收会话 | 另一个 AI 会话或 `sop-acceptance-reviewer` 子代理 | 按清单逐条亲自操作、记录事实、定级、写验收记录 | 不修问题，不改验收记录以外的文件 |

## 8 个步骤

| 步 | 做什么 | 主要产出（放在项目 `docs/`） | 用哪个 skill | 什么时候算完成 |
| --- | --- | --- | --- | --- |
| 1 | 确认需求 | `需求简报.md`（内容型产品再加 `knowledge/`） | `sop-discover` | 三句话讲得清；角色列全、有初步分端判断；目标有数字；"不做什么"至少 3 条；平台门槛查过 |
| 2 | 写 PRD | `PRD.md` | `sop-prd` | 每条功能有编号和优先级；多端的标了端、有权限表；待确认问题单列；产品负责人确认 |
| 3 | 方案与决策 | `specs/<阶段>/spec.md`、`设计规范.md` | `sop-spec` | 决定点全部有结论（多类角色的含"分几个端"），写回方案和交接文档"已定" |
| 4 | 定标准 | `执行标准.md`、`验收原则.md`、`验收清单.md`、项目专属开发 / 验收 skill | `sop-standards` | 执行标准、验收原则、验收清单（或等价文档）齐全，`CLAUDE.md` / `AGENTS.md` 指向它们；新项目还有验收记录目录、交接文档和项目专属开发 / 验收 skill |
| 5 | 小步开发 | 代码 + 交接条目 | `sop-develop`（项目有自己的开发 skill 时用项目的） | 7 项必做全部完成 |
| 6 | 独立验收 | `验收记录/YS-*.md` | `sop-accept` | 结论是"通过"或"有条件通过"，问题已登记 |
| 7 | 部署发布 | `部署说明.md`、发布说明、真机检查结果 | `sop-release` | 冒烟测试通过；真机检查结果记入交接文档 |
| 8 | 交接与反馈 | `交接文档.md`、新需求 | `sop-handoff` | 新会话只读交接文档就能接着干；反馈已整理进 PRD |

第 1–4 步只写文档、不写代码。第 5、6 步交替进行，验收不通过就回第 5 步。第 8 步贯穿全程。

## 判断现在在哪一步

### 先弄清项目自己的文档叫什么

很多项目的文档名和本 SOP 不一样。判断之前先读 `CLAUDE.md`、`AGENTS.md`、`.trae/rules/`、`.agents/`、`README.md` 和 `docs/` 目录，按**内容**找出下表每一项对应的文件。找到等价文档就用它，**不要再新建一份**；找不到才算缺。

| SOP 里的叫法 | 内容上要有什么才算 | 常见的其他名字 |
| --- | --- | --- |
| 需求简报 | 有哪几类角色、可衡量的目标、不做什么 | PRD 的背景与目标一节、产品方案 |
| PRD | 带编号的功能清单 | 产品方案、需求文档（.docx 也算） |
| 阶段方案 | 某个阶段的范围、规则、决定点和结论 | `specs/*/spec.md`、设计方案的某一章 |
| 执行标准 | 改代码时必须做的事、检查命令、完成的定义 | `.trae/rules/`、项目的 standards skill、AGENTS.md 里的规则 |
| 验收原则 | 证据要求、怎么判定、问题怎么定级 | 验收标准、acceptance 规则 |
| 验收清单 | 每个功能有可操作的步骤和预期结果 | 验收标准里的案例表、测试用例表 |
| 验收记录 | 每轮验收的结果和证据 | `验收记录/`、验收标准里的记录表、测试报告 |
| 交接文档 | 当前状态、未关闭问题、下一步 | 交接说明、进度、HANDOFF.md、README 的进度表 |

把对照结果告诉用户，并建议写进 `CLAUDE.md` / `AGENTS.md`，以后的会话就不用再找；装了硬性检查的，同时改 `.sop.json` 里的文档路径（见 `sop-standards` 第 9 步）。项目没有 `CLAUDE.md`，或 `CLAUDE.md` / `AGENTS.md` 没指向这些文档，也算一个要补的地方。

### 再按顺序检查

第一个缺的就是当前主线步骤：

1. 有需求简报或等价内容 → 没有就是第 1 步
2. 有带编号的 PRD → 没有就是第 2 步
3. **接下来要做的那个阶段**有方案，而且决定点都有结论 → 没有就是第 3 步。"接下来要做的阶段"看交接文档的下一步或 PRD 的里程碑；所有阶段都做完、只剩修问题时，跳过这一项
4. 有执行标准、验收原则、验收清单（或等价文档），`CLAUDE.md` / `AGENTS.md` 指向它们 → 缺任何一样就是第 4 步，只补缺的那样
5. 读交接文档的"当前状态"，**并用 git log、最近的验收记录和最近的报告核对它是不是最新的**；过期了，先用 `sop-handoff` 补上再往下判断。然后看：
   - 最近的代码变化还没有**独立验收** → 第 6 步
   - 有未关闭问题，或有新需求要做 → 第 5 步
   - 验收通过、还没部署或还没真机检查 → 第 7 步

"独立验收"指：由没写这批代码的会话或工具做，验收过程中没有改代码，结果按项目的验收原则判定并留了记录（记录放在哪个文件不重要）。开发会话自己验的、验的时候顺手改了代码的，都不算。

主线之外同时等着的事也要一起说，例如"主线在第 5 步；另外第 7 步的真机检查在等你做"。

已经有代码、但文档缺失的老项目：先补第 4 步的标准和第 8 步的交接文档，再按上面的顺序往回补 PRD；不要一边补文档一边改代码。

### 告诉用户

现在在第几步、依据是什么（引用文件和章节）、文档对照表（名字不一样时）、下一步具体做什么、要加载哪个 skill、有哪些事在等他做。

## 新项目初始化

在第 1 步的第一轮追问里顺带问一句"要不要我先搭好项目骨架"，同意后**只建这几样**：

```
项目根/
├── CLAUDE.md          ← 写明：改代码前加载开发 skill，做验收加载验收 skill；读哪些文档
├── AGENTS.md          ← 一句话："本项目规则见 CLAUDE.md"，给 Trae、WorkBuddy、Codex 等工具看
├── README.md          ← 一句话说明产品；运行方式等有代码后再补
└── docs/
    └── 交接文档.md     ← 用 sop-handoff 的模板，当前版本写"尚无代码"
```

其他文档到了对应步骤再建：需求简报（第 1 步）、PRD（第 2 步）、`specs/` 和设计规范（第 3 步）、执行标准 / 验收原则 / 验收清单（第 4 步）、验收记录目录（第一次验收时）、部署说明（第 7 步）。**不要提前建空壳**：只有标题、没有实际内容的文件不算完成，判断步骤时按"缺"处理。

另外第一轮要问清**项目代号**：小写英文、数字和连字符（例如 `gouhua`），用于项目专属 skill 的名字（`gouhua-dev`）和目录名。中文产品名照常用在文档里。

## 小项目可以轻一点

一个人、一个月以内能用上的项目，在不丢掉核心规矩（先文档后代码、人拍板、开发和验收分开、完成要有证据、交接文档）的前提下可以精简：

- 阶段方案只写必需的几节：要解决的问题、完成标准、范围、规则、怎么验收、决定点
- 执行标准和验收原则可以合成一份 `docs/开发与验收标准.md`，各写最关键的条目
- 验收清单只写 P0 功能和硬指标，其他等做到时再加
- 决定点"全部按推荐"时，交接文档"已定"记一条即可
- `AGENTS.md` 只指向 `CLAUDE.md`，不重复内容

开始前问产品负责人要完整版还是轻量版；拿不准就用轻量版，项目变大再补。

`CLAUDE.md` 的最小内容：

```markdown
# <项目名>

<一句话说明产品>。PRD 在 `docs/PRD.md`，当前状态在 `docs/交接文档.md`。

## 必须遵守
- 改代码时加载 `<项目>-dev` skill；做验收或复验时加载 `<项目>-acceptance` skill（第 4 步之前用 `sop-develop` / `sop-accept`）
- 改代码前先读 `docs/执行标准.md` 和 `docs/交接文档.md`
- 每次代码变化按执行标准做完 7 项才算完成
- 写代码的会话不给自己验收
- 全部回复用中文、说大白话
```

## 全局铁律（每一步都适用）

1. **先文档后代码**：功能没有 PRD 编号和验收条目，就不写代码。中途想加功能，先登记进 PRD
2. **人拍板**：产品规则、范围、要花钱的事、对外发布，都由产品负责人决定。AI 列选项、写推荐和理由，不自己挑一个就做
3. **小步走**：一次代码变化只做一件事，并编号（`KF-日期-序号`）
4. **完成要有证据**：测试通过、实际走一遍、写进记录才算完成；"代码写完了""应该没问题"不算
5. **开发和验收分开**：写代码的会话不给自己验收
6. **文档跟着代码走**：代码一变，交接文档、验收清单、验收原则都要检查；没改也要写明原因
7. **不放水**：不为了通过而放宽规则、删测试、改清单的预期结果
8. **记录不改写**：验收记录、历史决策写完不改，有误在下一条里说明
9. **外部动作由人做**：提交、推送、发布、部署只在产品负责人明确说了以后做；密钥、登录、付款、外部平台后台由人亲自操作，AI 写好步骤后停下
10. **可移植**：路径不写死在某台电脑上，规则写进项目里的文件，换会话、换电脑、换 AI 工具都能接着干
11. **遇到冲突就停**：PRD 和代码不一致、新行为没有验收条目、测试失败且修复会改变产品行为、改数据结构没有迁移或备份方案时，停下来问

第 3、4、7、8 条有机器把关：Claude Code 每一轮结束时跑 `sop-check` 并提醒；git 每次提交、CI 每次推送和发正式版时再跑一次，没做到就拦下。不要想办法绕过这些检查（例如 `git commit --no-verify`）；确实要跳过，由产品负责人决定。

## 和产品负责人沟通

- 全程用中文、说大白话；专业概念打个比方（"签名"就像给安装包"盖章"）
- 要问的问题一次问完，不要挤牙膏
- 给选项时 2–4 个，每个写清后果，推荐项放第一个并写理由；产品负责人可以不选，直接说自己的想法
- 每做完一段，用三五句话说清：做了什么、现在到哪了、还差什么、需要他做什么
- 大任务可以建议新开会话做，把前因后果写清楚交过去
