# 第 7 步：部署发布与真机检查

只发布验收通过的版本。发布步骤写成部署说明，上线后立刻跑冒烟测试；真机上的表现由产品负责人看。

## 发布前检查

- 交接文档"当前状态"里，要发布的版本有验收记录，结论是"通过"或"有条件通过"（有条件的，遗留问题产品负责人知道并同意）
- 产品负责人明确说了"部署 / 发布"
- 平台门槛已满足（主体资质、类目、备案、签名、隐私声明）；没满足就只能发开发版 / 预览版
- 发正式版前跑 `node scripts/sop-check.mjs --release`：最新一次代码变化必须有结论为"通过"或"有条件通过"的验收记录。用了 CI 模板的项目，打正式版标签时会自动跑这一项，不过就发不出去

例外：第一次部署为了打通流程，可以用还没验收的版本，但要产品负责人同意，并写进交接文档"已定"。

## 谁做什么

| AI 做 | 人做 |
| --- | --- |
| 写部署说明和冒烟脚本 | 登录平台、开通环境和数据库 |
| 打包（只打已提交的代码，例如 `git archive`） | 在 Secrets / 环境变量里填密钥、密码、令牌 |
| 配置 CI：测试、签名、体积检查、自动发布 | 在控制台点"部署""发布"，选版本 |
| 写发布说明 | 在真机、开发者工具、手机上试 |
| 上线后查日志、查配置是否生效 | 对外公开内容的最后确认 |

碰到"人做"的步骤，AI 写清楚一步步怎么做（点哪个菜单、填什么、怎么确认成功），然后停下等。密钥和密码不写进任何文件，也不要让用户把它发到聊天里。

## 做法

1. **写部署说明** `docs/部署说明.md`，按 [references/deploy-doc-template.md](references/deploy-doc-template.md)：从零开始的每一步、环境变量清单（名字、用途、去哪拿、要哪些权限）、冒烟测试、回滚方法、常见报错
2. **准备冒烟测试**：5–10 项最关键的检查，上线后几分钟内跑完。例：服务起来了、读写数据库、上传图片能公开访问、身份识别、运营后台能进
3. **打包或配 CI**：只打包已提交的代码；CI 里测试、lint、签名、体积检查任何一项失败就不出包
4. **先发预览版**：版本号带 `preview`（例如 `v1.0.4-preview.2`）或用平台的开发版 / 体验版；真机验收通过后才打正式版的号
5. **写发布说明**，按 [references/release-notes-template.md](references/release-notes-template.md)：这次包含哪些功能编号、已知问题、怎么安装或升级
6. **给产品负责人真机检查步骤**，按 [references/device-check-template.md](references/device-check-template.md)
7. **上线后**：跑冒烟测试；查运行日志有没有报错；用接口查一遍配置是否真的生效（环境变量名多一个空格、模板 ID 没存上，都不会报错但功能不工作）
8. **记录**：部署时间、版本号、对应提交号、冒烟结果、真机检查结果，写进交接文档"当前状态"和环境一节

## 常见坑

- **令牌权限不全**：发布令牌复制不全会 401，没开写权限会 403。部署说明里写清每个令牌要哪些权限、怎么确认
- **体积 / 资源快到上限**：余量不到 5% 时提前告诉产品负责人，让他选优化还是改规定，不要等构建失败
- **环境变量没生效**：保存时报错或名字带空格，平台可能照常部署旧配置。上线后用接口查一遍
- **把"没测"写成"通过"**：发布说明里写"真机已通过"，就必须有真机检查记录
- **开发机不等于运行机**：要在别的电脑上运行的，打包脚本、安装脚本、更新脚本都要能在一台全新的电脑上从零跑通；更新失败要能自动回滚；路径不写死

## 完成标准

- 部署说明和冒烟测试写好，冒烟全部通过
- 发布说明写好
- 产品负责人看过真机，结果记进交接文档
- 交接文档记下了线上版本、提交号、部署时间
